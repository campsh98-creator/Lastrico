# Open-source strategy for Lastrico by Motia

## Purpose

Open source is a product-learning, transparency, and community mechanism. It may improve
code, testing, documentation, accessibility, and road-data methods; it does not
automatically create adoption, trust, data quality, or a commercial business.

## Current and future boundary

**Current fact:** the Lastrico application repository is released under its stated licence
and contains the experimental Milan PWA. Existing contribution, conduct, governance, and
security documents remain authoritative.

**Planned subject to legal and technical review:** Motia may offer hosted services,
production routing infrastructure, native applications, enterprise tools, or an API. No
future component is assumed to be open or proprietary until an explicit licensing and
architecture decision is recorded.

## Component policy

| Component | Default direction | Required review |
| --- | --- | --- |
| Lastrico client and reproducible routing experiments | open where licence-compatible | security, provider terms, attribution |
| tests, documentation, accessibility tools | open | privacy and licence |
| community reporting schema and moderation method | transparent where safe | abuse and privacy |
| third-party map/routing data | governed by source licence; not automatically redistributable | provenance and redistribution |
| community-generated road information | publish only verified, consented/licensed fields | privacy, moderation, data quality |
| credentials, private user data, location histories | never public | security/privacy owner |
| production operations and security-sensitive configuration | disclose only what is safe | security owner |
| future commercial API/service | decision pending | business, licence, competition, community |

Open core, dual licensing, hosted-service differentiation, or a contributor licence
agreement must not be introduced implicitly. Each requires legal and community review.

## Contributor funnel

1. Discover a real issue or evidence asset.
2. Read current capability, limitations, licence, and conduct rules.
3. Choose code, testing, accessibility, documentation, translation, or road-data work.
4. Complete a labelled, bounded first contribution.
5. Receive specific review and opt-in recognition.
6. Take a repeat task.
7. Qualify for scoped trusted-review or maintainer responsibility.

## Maintainer responsibilities

- maintain a public roadmap and decision record;
- label beginner tasks with acceptance criteria;
- review licences, provenance, privacy, security, and supported modes/regions;
- respond or set expectations rather than leaving silent queues;
- explain rejections and conflicts of interest;
- publish release notes and recognise contributors with consent;
- retain accountable owners for routing, security, data, and releases;
- avoid using unpaid work as a permanent substitute for critical professional roles.

## Data contribution rules

Accept only data with a compatible source/permission, public-road scope, observation or
generation date, method, confidence, and non-sensitive evidence. New reports remain pending
until review and must not alter routing automatically. Missing data is unknown—not smooth,
safe, lit, current, or hazard-free.

Reject scraped/proprietary data without permission, personal addresses, continuous journeys,
licence plates, identifiable people, unverifiable claims, and evidence collected through
unsafe interaction while moving.

## Community health

Track time to first response, first-contribution completion, repeat contributors, review
latency, accepted/rejected work with reasons, contributor retention, moderation backlog,
security response, and community-conduct incidents. Star count alone is not a health metric.

Review the open-source boundary before each commercial milestone and publish material
changes before requesting community work affected by them.
